# Mobile Google Maps setup

## Why Google Maps is still required

Google Maps is **not** used on the web front end. The front end renders maps with
`maplibre-gl` (OpenFreeMap/MapLibre tiles) and the backend geo proxy reports
`mapsProvider: 'maplibre'`. Nothing in `frontend/` needs a Google key, and
`frontend/.env.example` ships `VITE_GOOGLE_MAPS_API_KEY` empty on purpose.

Mobile is different. `mobile/src/screens/driver/DriverHomeScreen.js` and
`mobile/src/screens/employee/EmployeeHomeScreen.js` both import
`react-native-maps`, which uses the **Google** provider:

```js
import MapView, { Marker, Polyline } from "react-native-maps";
```

Expo injects `android.config.googleMaps.apiKey` into `AndroidManifest.xml` as
`com.google.android.geo.API_KEY`. Remove it and the driver/employee maps render
blank on a real device.

## The key is not a secret, but it must be restricted

A Google Maps key used by a mobile app is compiled into every APK/IPA and can be
extracted from the binary by anyone. Removing it from git stops the leak into
source control, but it cannot stop the leak from the app itself. Therefore the
real control is **restriction** in the Google Cloud console. Until that is done,
the key is effectively public and can be used to consume your quota or generate
a bill.

## Required restrictions

Apply to the key used for mobile builds:

1. **APIs** - enable only what is used:
   - Maps SDK for Android
   - Maps SDK for iOS
   - (Optional) Places API, if address autocomplete is wired up on mobile
   - Disable: Geocoding, Distance Matrix, Roads, Street View, and every
     Directions API unless explicitly needed. These are the expensive ones.
2. **Application restrictions**
   - Android: restrict to the three package names, each with the **release
     signing certificate SHA-1**:
     - `com.getinroute.employee`
     - `com.getinroute.driver`
     - `com.getinroute.school`
   - iOS: restrict to the same three bundle identifiers.
3. **Quota / billing** - set a daily request and cost alert so an abuse spike is
   visible immediately rather than at month end.

Note: the key currently embedded in the already-published APKs/AABs is
necessarily still in those binaries. Restricting the key is what neutralises it.
Rotating it is only required if the key is considered compromised, or if you
want the old binaries to stop working.

## Supplying the key to builds

The key is no longer committed. `mobile/app.config.js` reads it from the
environment and **fails the build** for a production/profile store build when it
is missing, so a release can never silently ship a blank map.

For EAS-hosted builds, store it as a plaintext EAS environment variable (it is
not a secret in the usual sense - it ships inside the app):

```
eas env:create --environment production --name GOOGLE_MAPS_API_KEY --visibility plaintext
```

For local builds, put it in `mobile/.env.local` (gitignored) or export it before
running `expo run:android` / `eas build`.

## Generated native projects

`mobile/android/` and `mobile/ios/` are generated by `expo prebuild` and are
gitignored. Never edit `AndroidManifest.xml` or `Info.plist` by hand to add a
key - it will be overwritten on the next prebuild. Change `app.config.js` only.
